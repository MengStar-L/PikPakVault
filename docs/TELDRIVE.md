# TelDrive 文件夹同步

把 [TelDrive](https://github.com/tgdrive/teldrive) 中的指定文件夹上传至当前 PikPak 账号。同步是单向复制；不在 TelDrive 创建分享、不删除源文件，也不传播源端删除。

## 配置

1. 打开侧栏 **TelDrive 同步 → 添加监控**。
2. 填写你的 TelDrive 站点地址，例如 `https://teldrive.example.com`。可含反向代理的子路径，末尾 `/api` 可省略。
3. 在已登录 TelDrive 的浏览器开发者工具中，打开 **应用 / 存储 → Cookie → access_token**，复制该 Cookie 的值。只需值，不要粘贴整个 Cookie 请求头。该凭据等同于 TelDrive 登录会话。
4. 点击 **连接并选择文件夹**，浏览并选择当前文件夹。支持选择根目录，自动包含子目录。
5. 选择资源库中的目标文件夹。监控目录中的内容会直接保存在这里，不额外套一层监控目录名；实际位于设置中的 PikPak 专用根目录下。
6. 选择 **仅手动同步**（默认），或每 5 分钟至每 7 天同步。点击 **保存监控**。
7. 点击 **立即同步**，查看扫描状态；在 **传输任务** 中查看逐文件进度、暂停、取消或重试。文件也会直接出现在目标目录中并显示传输状态。

认证过期时，打开监控卡片的 **配置**，填写新的 access_token；留空表示保留原认证。关闭自动同步不取消已经排队的任务。既有监控的来源与目标固定，需要更换时关闭旧规则并新建。

## 同步与恢复规则

- 完整读取所有相关分页后才登记资源、创建上传任务。中断或检测到分页变化时不提交部分目录。
- 按 TelDrive 文件 ID 和监控规则去重，不按本地保存路径去重。文件或整目录移出原同步目录、重命名后不会重复上传；监控的目标目录只决定新资源的初始位置。
- 已登记资源独立检查，即使原本地目录已删除或源文件已移出监控目录，仍通过保存的 TelDrive 文件 ID 追踪。原本地目标删除后暂停新资源登记，已经移出的资源仍可恢复。
- 确认 PikPak 副本缺失后，恢复跟随监控同步模式：自动监控在定时同步或完整远端检查后补回；手动监控在点击“立即同步”或恢复中心确认后补回。远端分页中断、网络错误、位置差异、内容冲突和首次上传未完成不会触发重新上传。
- 首次上传完成前，文件显示传输状态，不计入待恢复。排队、暂停、失败或等待处理的任务继续保留上传会话，请在原任务中重试；取消后才允许另建恢复任务。恢复预览和执行会跳过已有任务的文件，整目录恢复也遵循此规则；其他账号的任务不影响当前账号恢复。
- 本地重命名、移动、收藏和播放进度继续保留。来源记录与目标路径分开保存，例如“同步目录/A.mp4”移到“收藏/B.mp4”后，缺失时仍从原 TelDrive 文件获取内容，恢复到“收藏/B.mp4”。源端移动、改名不覆盖本地目标路径。
- 源文件同一 ID 的内容变化会提示待处理，保留已有副本。需要同步新版本时，在 TelDrive 中保存为新文件 ID。没有上游内容哈希时使用大小与更新时间检测变化。
- 同名目标不覆盖。目录创建和文件上传直接使用最终名称，不反复创建、移动中转目录。请求响应丢失时先核对结果；无法唯一确认时暂停。
- 切号前创建的任务始终绑定原账号并暂停；切号后新扫描使用当前账号，补建对应目录和文件。自动同步开启时，这也适用于后续定时扫描。
- 本地主动回收站中的文件或目录会被跳过，不自动复活。TelDrive 源文件被删不会删除已经保存到 PikPak 的副本。
- 自动补回和恢复中心共用恢复流程，先核对现存副本和回收站，再重新下载上传；恢复目录时只处理确认缺失的条目。申请上传和完成核验时重新读取最新目录与名称，传输期间再次整理文件也不会重复申请上传凭证。
- 重新上传仍会尝试 GCID 命中，最终核对大小与 GCID。TelDrive 会话失效、源内容变化或源文件删除时，保留最后目标路径和失败原因，修复来源后重试原任务。

## 传输与资源消耗

程序自行下载并管理 **aria2 1.37.0**，不会使用系统 aria2，也不连接用户已有 RPC。首次同步时按 Linux amd64/arm64 或 Windows amd64 选择固定安装包，验证安装包及可执行文件的 SHA-256 后才运行。Linux 使用 abcfy2/aria2-static-build 静态发行包，Windows 使用 aria2 官方发行包；下载来源与校验值随程序版本固定。

默认位置均以 `vault` 可执行文件所在目录为准：

- `runtime/aria2/1.37.0/`：专用 aria2 程序，自动安装并验证。
- `downloads/<实例ID>/<任务文件ID>/`：文件缓存、`.aria2` 断点记录和任务归属信息。

Linux systemd 默认对应 `/opt/pikpakvalue/runtime/aria2/1.37.0/` 与 `/opt/pikpakvalue/downloads/`。程序根目录与主程序仍归 root 所有，服务用户只可写这两个子目录。自定义部署可设置 `VAULT_PROGRAM_DIR`，并同步调整 systemd 可写目录。Docker 使用 `/opt/pikpakvalue/` 下独立的 runtime、downloads 数据卷，升级保留数据卷即可。

传输顺序为 **aria2 下载 → 本地计算 GCID → PikPak 分片上传 → 大小及 GCID 核验 → 清理缓存**。正常情况下一份文件只从 TelDrive 下载一次，上传直接读取本地缓存；秒传命中则不再上传文件内容。服务器需要承担一份文件的下行流量、未命中秒传时的一份上行流量以及临时磁盘空间，断线重试可能增加流量。GCID 与 TelDrive BLAKE3、磁链 BTIH 不同。

每次串行下载一份文件，单连接，aria2 遇到中断最多重试 8 次，不无限重试或频繁增加连接。下载进度、速度、校验和上传阶段都在原传输任务中显示。下载前检查剩余空间，并额外保留 64 MiB；暂停、失败、切号和服务重启时保留缓存及断点。子进程只在任务执行期间运行，停止后才允许释放缓存。

TelDrive 页面的 **清理闲置缓存** 只处理已停止任务的缓存，不触碰源文件、云端副本或排队/运行中的任务。正在上传时需先暂停并等待读写停止；清理后重试需要重新下载。上传会话和原任务继续保留，避免重复向 PikPak 申请文件。

上游凭据留在 Go 进程内：aria2 只访问临时的本机文件流入口，RPC 仅监听回环地址并使用每次随机口令，不开放额外公网端口。程序和系统 aria2 相互独立。

可由服务用户提前安装专用组件（可选，不启动网盘服务）：

```bash
sudo -u pikpak-vault /opt/pikpakvalue/vault prepare-aria2
```

从 0.3.1 或更早版本升级前，先执行新版包中的 `sudo bash deploy/prepare-runtime.sh` 配置专用目录权限。之后的更新保留 runtime、downloads；无需 Go、Node、rclone 或 Telegram 客户端。

## 备份与兼容性

TelDrive access_token 和上传临时凭证使用资源库密钥加密，不返回到浏览器，不写入操作日志。完整备份包括监控、来源、认证及上传状态；专用 aria2 和临时下载缓存不打入备份，迁移后自动重新下载，导入时重新加密，并暂停任务等待核对。来源 JSON 不含凭据。

此功能升级数据库至 schema 2，支持导入 schema 1 的旧备份。旧版本不能打开升级后的数据库，降级应恢复升级前配套数据库与密钥。

接口按 TelDrive 公开 OpenAPI 和服务实现核对（参考提交 `d400a2d`）。自动化测试使用模拟 TelDrive 与 PikPak，覆盖分页、鉴权、Range、分片中断、恢复、切号和备份迁移。真实 TelDrive 实例与真实 PikPak 上传仍需配置后联调，上游私有上传接口可能变化。
